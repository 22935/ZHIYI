用户要求在现有系统里规划「类虚拟宠物」角色：进度问询 / 基础聊天 / 情感陪伴 / 任务分发，重点要形象加载、对话能力、低耦合集成。产出

### 调研得到的关键事实（后续复用，勿重复查）
- 项目里**已有三套角色资产**：`frontend/src/lib/grok-character/`（程序化 SVG，39 状态/18 形状/11 配色）、
  `components/landing/GlassConstellation.vue`（落地页已有「对话→表情」联动 + 唤醒词 + 懒加载 chatStore）、
  `tools/tui/src/kinlin_tui/mascot.py`（4 角色 × 6 情绪 ASCII + 中文对白池）。`DigitalHuman.vue` 已冻结。
- 最小接入点：前端 `App.vue` 的 `<ZoomIndicator />` 同级挂 `v-if="!isPublicRoute"` 的全局浮层（App.spec.ts 禁止公开路由实例化 chatStore）；
  后端 `apps/agent/app/main.py` 一行 `include_router(create_companion_router(ports=...), prefix="/ai")`。
- `/ai/**` 由 Java `AiServiceProxyController` 通配透传，新增路径**零 Java/代理改动**；
  `/api/agentos/v2` 的 Controller 被 `ArchitectureGuardTest` 冻结为恰好 6 个，禁止新增；全仓禁 WebSocket，只能 SSE。
- 硬约束：`features/mission/architecture.spec.ts` 全量扫描源码禁止 `startWorkflowAsync(`、`'/missions'` 等字面量；
  ADR-001 引用优先（气泡/事件不得含正文与密钥）；PR-UI-02「不暗改普通 Chat API」；项目无 webhook，主动播报只能订阅既有 `/runs/{id}/events` SSE。

### 方案核心决策
- 定位为**接入层能力域**（只读消费者 + 受控意图旁路），ExecutionRuntime 仍是唯一执行真源。
- 四层：表现层 / 能力编排层（Python `app/companion/`，只依赖 Port 协议）/ 适配层（复用既有只读投影与 LLMGateway）/ 平台内核（零改动）。
- **语义状态中间层** decoupling：业务只发 8 个 CompanionState，皮肤 manifest 的 `stateMap` 负责映射具体形象 → 换形象不改业务。
- **任务分发不自己发**：意图卡 → 用户确认 → 深链交给既有统一 Mission Launcher（PR-UI-01），避开启动字面量守卫与 JWT 身份链。
- 解耦的可验证定义：**删掉 3 个 companion 目录 + 2 行注册后，既有测试全绿**。
- 阶段：P0 只读陪伴（零后端）→ P1 独立对话域 → P2 任务确认卡 → P3 皮肤/语音（Electron media 权限全拒，需安全评审）。
