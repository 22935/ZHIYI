# AgentOS 架构冗余与错位分析（2026-11-09）

> 对照对象：`apps/agentOS/README.md` 的设计规则与 `docs/当前实现梳理.md`（2026-11-08）。
> 范围：仅 `apps/agentOS` 的 Python 内核（`src/`、`service/`、`tests/`）与两个 TS 项目。
> `references/open-source/` 是调研快照，不计入内核冗余分析。

## 0. 一句话结论

设计意图是「薄编排 + 自包含部件 + 唯一共享合同层」，但现状是：**`runtime/` 变成了承载身份/工作区/规划引擎的胖编排层、`contracts/` 被部件级 schema 撑大、`support/acg/` 越权成了事实上的 ACG 规划合同层，且两个 TypeScript 项目混进了 Python `src/`**。文件总数从设计的约 60 个内核文件膨胀到 `src/` 下约 370 个 `.py`（components 131 / runtime 44 / contracts 38 / support 30 / adapters 29 / domain 11 / tools 8 / storage 5），层次因此显得不清。

## 1. 设计 vs 现状总览

| 维度 | 设计（README） | 现状 | 偏差 |
| --- | --- | --- | --- |
| 部件数 | 9（task_manager + 8） | 12 | `task_manager`→`mission_manager`；新增 `attachments`/`content`/`evolution`/`model_partition` |
| `runtime/` 文件数 | 4 | 44 | 远超「薄编排」，承载身份/工作区/规划子系统 |
| `contracts/` 文件数 | 8 | 38 | 大量部件级 schema 进入共享层 |
| `src/domain/` | 无 | 有（11） | 新增领域实体 + 仓储接口层 |
| `src/storage/v2/` | 无（仅 `adapters/storage`） | 有（5） | 新增 Identity V2 存储层 |
| `service/` 位置 | `src/service/agents/` | 仓库根 `service/agents/` | 文档与实际不一致 |
| `config/` | 顶层列出 | 不存在 | 设计条目失效 |
| 顶层 TS 项目 | 无 | `src/hands/`、`src/oscode-context/` | 混入 Python `src/` |

## 2. 放错位置（misplaced）

### 2.1 `support/acg/` 越权为事实上的跨部件合同层 ⚠ 违反设计
- 设计规则明确：`support/ 只承载历史运行时配套；不得新增跨部件合同`。
- 现状：`support/acg/` 有 9 个文件（`schema.py` 定义 `StepNode`/`ControlNode`/`ACGEdge`/`RuntimeBlueprintSpec` 等规划期类型、`models.py`/`planning.py`/`graph.py`/`validation.py`/`capabilities.py`/`semantic_profile.py`/`native_capabilities.py`）。
- 同时 `contracts/` 又定义了编译/运行期 ACG 类型（`compiled_acg.py` 的 `CompiledNodeSpec`/`CompiledEdge`/`CompiledACGPackage`，`workflow.py` 的 `Blueprint`/`RuntimeGraph`）。
- **结论：ACG 类型「分裂脑」——规划 schema 在 `support/acg`，运行 schema 在 `contracts`。** 应把 `support/acg` 的规划契约迁移到 `contracts/acg_schema.py`（或 `contracts/acg/` 包），`support` 仅保留兼容导出。`docs/当前实现梳理.md` 已将该拆分列为边界债务。

### 2.2 两个 TypeScript 项目混入 Python `src/` ⚠ 强烈建议迁出
- `src/hands/` 与 `src/oscode-context/` 均自带 `node_modules/`、`package.json`、`tsconfig.json`，是独立的前端/上下文工具，与 Python 内核无包级依赖。
- 置于 `src/` 下会污染 Python 包树、干扰 pytest 收集与覆盖率统计，且模糊「`src` = Python 内核」的隐含约定。
- 建议：迁至 `apps/` 下独立目录（如 `apps/hands`、`apps/oscode-context`）或在 agentOS 根建 `integrations/`。`adapters/hands_http.py`、`adapters/hands_patch.py` 已通过 HTTP 引用，迁走后仅需同步路径。

### 2.3 `service/` 位置与文档不一致
- 设计写 `src/service/agents/`，实际是仓库根的 `service/agents/`（`base.py`/`registry.py`）。`docs/当前实现梳理.md` 已按根 `service/` 描述，故以根为事实。建议统一：要么移动为 `src/service/`，要么修正 README 的树。

### 2.4 `config/` 设计列出但不存在
- README 顶层列出 `config/ 运行配置`，但 agentOS 下无此目录（运行配置可能落在 `apps/agent` 或环境变量）。建议补建或删除该条目，避免误导。

## 3. 功能 / 职责重复（redundant）

### 3.1 同名文件 `contract_repair.py`（语义不同，易混淆）
- `src/components/recovery/contract_repair.py`：JSON 合同载荷的「确定性无损修复」（object↔array envelope / 显式默认值）。
- `src/adapters/model/contract_repair.py`：模型输出字段的「保守修复计划」（`FieldRepairPlan`，只改简单显式字段）。
- 二者都基于 `contracts.communication.validate_contract_payload`，但职责不同。同名是命名冲突，建议重命名为 `payload_repair.py` 与 `model_field_repair.py`，或在 `contracts/` 下做统一修复工具后让两边调用。

### 3.2 ACG 类型分裂（规划 vs 编译/运行）
- 已述于 2.1。属「重复定义 + 错位」叠加：同一概念（ACG 节点/边/蓝图）在两个根（`support/acg` 与 `contracts`）各有一套类型，跨层传递时易因字段不一致踩坑。

### 3.3 `contracts/` 膨胀：部件级 schema 进入共享层
- 设计：跨部件共享才进 `contracts`；部件自包含 `models`。
- 现状：`contracts/` 含明显「部件专属」的 schema：`mission_semantic.py`/`mission_revision.py`（mission_manager）、`model_partition.py`（model_partition）、`content.py`/`attachments.py`（content/attachments）、`evolution.py`（evolution）、`htn.py`/`horizon.py`/`planner_actions.py`/`planning*.py`（planner）。
- 对照：`planner` 同时有本地 `models.py` 与 `contracts/planning*.py`；而 `mission_manager` **没有本地 `models.py`**，类型全在 `contracts`。两种模式并存，缺乏统一判据。
- 建议：明确「何时应进 `contracts`」的硬规则（跨 ≥2 部件复用 / 跨进程传输才进），其余下沉到部件 `models.py`；`mission_manager` 应补 `models.py` 作为本地类型门面。

### 3.4 `adapters/` 中「模型」相关文件过多且分散
- 根级：`model_adapter.py`、`model_runtime.py`、`model_compatibility.py`、`openai_runtime.py`、`prompt_runtime.py`、`guarded_model.py`。
- 子包 `model/`：`native.py`、`native_prompt.py`、`prompt_context.py`、`contract_repair.py`。
- 共 11 个文件围绕「模型」，职责有重叠风险（`native` vs `openai` vs `prompt` runtime；`model_adapter` vs `model_runtime`；`guarded_model` 与 `model_adapter` 的边界）。建议梳理为单一模型适配入口 + 明确各 runtime 边界，或合并 `guarded_model` 与 `model_adapter`。

## 4. 冗杂 / 膨胀（verbose）

### 4.1 `runtime/` 44 文件，违反「薄编排不承载领域算法」
- 设计明确 `runtime/ 只负责装配与编排，不承载领域算法`。
- 现状 `runtime/` 内含：
  - 身份/工作区子系统：`runner`/`identity_projection`/`workspace`/`queries`/`query_models`/`reconciliation`/`resume_projection`/`state`/`state_persistence`
  - 规划循环：`planning_loop`/`planning_application`/`planning_interaction`/`planning_observation`/`planning_operations`/`planning_wait`/`planning_commit`/`planner_bridge`/`planner_input_adapter`/`initial_planning_sources`
  - 图生命周期：`graph_activation`/`graph_handoff`/`graph_materialization`/`graph_revision`
  - 语义修订：`semantic_patch`/`semantic_revision`；许可：`execution_permit`/`permit_recovery`
- 相当于把「规划引擎 + 身份子系统 + 图版本管理」都塞进编排层。
- 建议：将 identity/workspace 子系统抽到 `components/identity`（或 `domain` 旁），将 `planning_*` 收敛到 `planner` 部件的运行时门面，`runtime/` 仅保留 `workflow_runtime`/`bootstrap`/`dependencies`/`ports`/兼容性层。

### 4.2 `planner/` 29 文件（含 `topology/` 9 文件子编译器）
- 设计 8 文件 → 现状 29 文件。`topology/`（audit/binding_solver/compiler/errors/gate/model/repair/validator）已是一套独立的「拓扑编译/校验」子系统，规模接近一个部件。
- 同时 `planner` 内并存多种规划范式：`semantic_planner`/`semantic_patch_planning`/`react_loop`/`horizon`/`htn`，概念重叠、入口分散。
- 建议：评估 `topology/` 是否独立为 `components/acg_compiler` 或并入 `tools`；其余语义规划按需归并，避免单部件内 4+ 种规划范式并存。

### 4.3 `contracts/` 38 文件粒度偏细
- 图生命周期被拆成 `graph_activation`/`handoff`/`materialization`/`revision` 四个合同 + 对应 `runtime/` 四份 + 对应 `support/stores/*_store.py` 四份，「三层各一份」。
- 功能清晰但文件数高、改动易漏。建议合并为单一 `graph_lifecycle.py` 合同 + 单一存储模块，降低镜像维护成本。

## 5. 收敛优先级

**P0（先止住恶化）**
1. 2.2 迁出 `src/hands`、`src/oscode-context` 两个 TS 项目，明确 Python `src/` 边界。
2. 2.1 冻结 `support/acg` 新增，规划迁移到 `contracts/acg_schema`。
3. 3.1 重命名两个 `contract_repair.py`。

**P1（结构回归设计）**
4. 4.1 把 identity/workspace/planning 子系统从 `runtime/` 抽离。
5. 3.3 明确 `contracts` 准入判据，`mission_manager` 补 `models.py`。

**P2（长期整洁）**
6. 4.2 `planner/topology` 独立或归并；4.3 图生命周期三层合流。
7. 2.3 / 2.4 文档与目录对齐（`service/` 位置、`config/` 条目）。

## 6. 明确不属于冗余（勿动）
- `src/storage/v2/` 与 `src/support/stores/` 是有意隔离的两套存储层（前者服务 Identity V2，后者服务主执行引擎 `workflow_runtime.py`），schema 与仓储类型均不同，按 `docs/当前实现梳理.md` 不应合并。
- `src/domain/` 与 `contracts/` 是「接口(contracts) vs 实现(domain)」的分层，不是重复定义，不要「去重」合并。
- `tools/` 7 文件完全符合设计（ACG 导出/序列化/绘图），是最干净的一层。
