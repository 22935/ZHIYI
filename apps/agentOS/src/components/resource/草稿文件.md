资源器的核心不是“直接执行任务”，而是把一次工作流步骤从“需要什么能力”变成“由哪个可执行 Runtime 执行”，并维护资源身份、健康、容量、凭据和观测状态。

它的边界可以这样看：

```text
上游：Planner / 编译产物 / Workflow Runtime
  -> BindingManifest
  -> ExecutionRequirement

资源器：ResourcePlane + ResourceBinder
  -> Runtime 候选筛选
  -> 健康与容量校验
  -> 租约分配
  -> ExecutionBinding

下游：本地 Agent Runtime 或远程 HTTP Runtime
  -> 实际执行
  -> AgentOutput
  -> 执行结果观测回写 ResourcePlane
```

## 上下游职责

上游首先是编译后的 `BindingManifest`。`RuntimeBindingService.prepare()` 为每个步骤生成 `ExecutionRequirement`，其中包含能力、Runtime 类型、数据域、信任级别、位置、模型需求等约束；它不会提前锁定具体资源。对于本进程的 Agent，会先把 Agent 注册表投影成 `runtime:embedded-agents` 这个 `EXECUTION_BACKEND` Runtime。见 [binding.py](E:/Project/Kinlin_AI/apps/agentOS/src/runtime/binding.py) 和 [embedded_runtime.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/resource/embedded_runtime.py)。

资源器本体由 `ResourcePlane` 管理三类对象：

| 对象 | 含义 | 静态数据 | 动态数据 |
|---|---|---|---|
| `Node` | 设备、边缘节点或云节点 | 位置、信任级别、区域、算力、远程执行策略 | 心跳、CPU/GPU、排队数、状态、失败次数 |
| `Runtime` | 真正可调度的执行后端/模型服务/工具服务 | 能力、容量、端点、宿主节点、信任级别 | 空闲槽位、利用率、可靠性、延迟、观测序号 |
| `ModelEndpoint` | 可绑定的模型路由 | provider、model、特性、上下文长度、成本 | 主要通过版本和启用状态管理 |

这些合同定义在 [resource.py](E:/Project/Kinlin_AI/apps/agentOS/src/contracts/resource.py)，资源服务逻辑在 [service.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/resource/service.py)。

下游分两类：

- 本地 Runtime：例如进程内 Agent 运行时，不需要 HTTP 调用；执行器根据绑定在本地 Agent 注册表中解析角色。
- 远程 Runtime：根据 `RuntimeProfile.endpoint` 构造 `HttpResourceExecutionAdapter`，向远端 `/execute` 发起带 HMAC 签名的请求。见 [resource_execution.py](E:/Project/Kinlin_AI/apps/agentOS/src/adapters/resource_execution.py)。

## 一次完整请求的数据变化

以下以“工作流中一个 READY 步骤，被分配给远程 Runtime 并执行完成”为例。

### 1. 编译/准备阶段：任务声明转为资源需求

Planner 或编译器先产生类似的绑定意图：

```json
{
  "stepId": "step:review",
  "requiredCapabilities": ["exec.agents", "legal.review"],
  "agentNodeIds": ["legal-reviewer"],
  "maxConcurrency": 1
}
```

`RuntimeBindingService.prepare()` 将其变成并写入 `run.execution_state["bindingRequirements"]`：

```json
{
  "step:review": {
    "requiredCapabilities": ["exec.agents", "legal.review"],
    "runtimeKinds": ["execution_backend"],
    "domain": "legal",
    "preferences": {
      "agentRole": "legal-reviewer"
    },
    "policyMetadata": {
      "source": "compiled-binding-manifest",
      "stepId": "step:review",
      "agentNodeIds": ["legal-reviewer"],
      "maxConcurrency": 1
    }
  }
}
```

关键变化是：

```text
BindingManifest
  -> ExecutionRequirement
  -> run.execution_state["bindingRequirements"][stepId]
```

这里的 `agentRole` 只是排序提示，不是资源身份。真正决定某个 Runtime 是否有资格的，是能力、类型、位置、信任、区域、Owner Scope、远程执行策略等硬约束。

### 2. 资源登记阶段：远程服务变成可调度对象

远程 Runtime 在首次登记时提供：

```json
{
  "runtimeId": "runtime:edge:worker-01",
  "nodeId": "node:edge:shanghai-01",
  "kind": "execution_backend",
  "placement": "edge",
  "capabilities": ["exec.agents", "legal.review"],
  "capacity": 4,
  "endpoint": {
    "protocol": "https",
    "address": "https://edge.example.com/execute",
    "authReference": "resource-credential:runtime:edge:worker-01"
  },
  "ownerScope": "tenant:acme"
}
```

`ResourcePlane.register_remote_runtime()` 会执行以下变化：

```text
RuntimeProfile
  -> 校验 Node 存在、placement 一致、Runtime trust 不高于 Node trust
  -> 生成或接收 credentialId + secret
  -> secretDigest = SHA-256(secret)
  -> encryptedSecret = Fernet(secret)
  -> RuntimeProfile.metadata.registrationId = 稳定配置指纹
  -> 原子写入 Runtime、RuntimeSnapshot、CredentialRecord
```

持久化后的关键形态：

```text
plane_runtimes:
  runtime_id
  profile_json
  snapshot_json
  version = 1

resource_credentials:
  resource_id
  credential_id
  owner_scope
  secret_digest
  encrypted_secret
  created_at
```

明文 `secret` 只在注册响应中返回一次；后续数据库中保存的是摘要和密文，不在 `RuntimeProfile` 或普通执行响应中暴露。逻辑见 [service.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/resource/service.py) 与 [store.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/resource/store.py)。

### 3. READY 调度阶段：需求转为候选集合

当步骤进入 READY，`ResourceBinder.evaluate()` 遍历所有 Runtime，并为每个 Runtime 读取：

```text
RuntimeProfile
RuntimeSnapshot + version
RuntimeHealth
NodeProfile
NodeHealth
ExecutionRequirement
```

对每个 Runtime 进行硬约束过滤。典型过滤项包括：

```text
Runtime.enabled
Runtime.kind 是否满足
能力集是否包含 requiredCapabilities
Node 是否 enabled
Node 健康是否可调度
Runtime 健康是否正常
availableSlots 是否大于 0
placement / trust / 数据域 / region / owner scope 是否满足
是否允许远程执行
是否被显式排除
模型端点是否满足模型需求
```

不合格的 Runtime 不会丢失，而是变成可审计的 `CandidateDecision`：

```json
{
  "resourceId": "runtime:edge:worker-01",
  "accepted": false,
  "reasons": ["NODE_OFFLINE", "MISSING_CAPABILITY"],
  "reasonDetails": ["节点离线", "缺少 legal.review 能力"]
}
```

合格 Runtime 则得到分数，分数受位置偏好、可靠性、延迟、利用率和软路由提示影响：

```json
{
  "resourceId": "runtime:edge:worker-01",
  "accepted": true,
  "score": 0.82
}
```

这一层是只读的：不会修改 Runtime 状态，也不会占用容量。核心实现见 [binder.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/scheduler/binder.py)。

### 4. 绑定阶段：候选转为租约和不可变绑定

`ResourceBinder.bind_ready()` 按分数顺序尝试候选 Runtime。

对第一个可分配 Runtime：

```text
1. 读取 RuntimeSnapshot(version = N)
2. 请求 LeaseCoordinator.acquire(...)
3. 再读取 RuntimeSnapshot
4. 只有版本仍为 N 才继续
5. 创建 ExecutionBinding
```

数据变化：

```text
LeaseCoordinator:
  active_leases[runtime:edge:worker-01] += 1

Run execution_state:
  resourceBindings[stepId] = ExecutionBinding
```

典型绑定对象：

```json
{
  "bindingId": "binding:run-123:step-review:attempt-1",
  "runId": "run-123",
  "stepId": "step-review",
  "attemptId": "attempt-1",
  "resourceId": "runtime:edge:worker-01",
  "runtimeKind": "execution_backend",
  "nodeId": "node:edge:shanghai-01",
  "placement": "edge",
  "trust": "trusted",
  "snapshotVersion": 17,
  "leaseId": "lease:run-123:step-review:attempt-1:runtime:edge:worker-01",
  "leaseVersion": 1,
  "modelBinding": null
}
```

这里的 `snapshotVersion` 很重要：它把“调度时看到的资源版本”冻结下来。如果资源在租约取得后发生变化，绑定过程会释放租约并尝试下一个候选，避免基于过期状态执行。

### 5. 远程执行请求：绑定转为 HTTP 负载和签名

执行器读取 `ExecutionBinding.resourceId`，根据该 Runtime 的 `endpoint` 选择远程 HTTP Adapter。

发送前，会将 `AgentRunContext` 压缩成远程执行负载，而不是透传整个运行时对象：

```json
{
  "runId": "run-123",
  "missionId": "mission-456",
  "stepId": "step-review",
  "attemptId": "attempt-1",
  "commitId": "commit-789",
  "agentName": "legal-reviewer",
  "capability": "legal.review",
  "goal": "审查合同风险",
  "input": {
    "contractId": "contract-001"
  },
  "evidenceRefs": ["evidence:source-01"]
}
```

Adapter 从 `ResourcePlane.current_signing_credential(resourceId)` 读取当前凭据。每次执行都重新读取，因此凭据轮换会在下一次请求自动生效。

请求中增加：

```text
Content-Type: application/json
X-Resource-Id: runtime:edge:worker-01
X-Resource-Credential: rc_xxx
X-Resource-Timestamp: 1794210000
X-Resource-Nonce: <随机值>
X-Resource-Signature: <HMAC-SHA256>
```

签名原文是：

```text
METHOD
PATH
TIMESTAMP
NONCE
SHA256(BODY)
```

然后使用 `SHA256(secret)` 作为 HMAC key。相关代码见 [resource_signing.py](E:/Project/Kinlin_AI/apps/agentOS/src/contracts/resource_signing.py) 和 [resource_execution.py](E:/Project/Kinlin_AI/apps/agentOS/src/adapters/resource_execution.py)。

### 6. 远端入口：身份、时间、完整性、重放保护

远端服务应使用 `ResourceRequestAuthenticator.authenticate()` 验证该请求，验证顺序不可交换：

```text
1. resourceId 是否存在
2. credentialId 是否匹配当前资源
3. timestamp 是否在 5 分钟允许偏差内
4. 根据 method/path/timestamp/nonce/body 重算 HMAC
5. hmac.compare_digest 比较签名
6. 原子写入 nonce
```

只有第 1 至第 5 步都通过，才会消费 nonce。

nonce 的状态变化：

```text
(resource_id, nonce) 不存在
  -> 插入 resource_auth_nonces
  -> expires_at = signed_at + clock_skew
```

如果唯一键已存在，鉴权失败为 `ResourceRequestReplay`。如果签名、凭据或时间戳错误，则不会消费 nonce。实现见 [auth.py](E:/Project/Kinlin_AI/apps/agentOS/src/components/resource/auth.py)。

### 7. 执行结果回流：输出、健康和观测快照

远端成功返回必须是 HTTP 200，且 body 能严格解析为 `AgentOutput`。非 200 或格式不完整的响应会转成 `ResourceExecutionError`，其中一部分错误被标记为“执行结果未知”，防止系统误判为未执行后直接重复执行。

执行完成后，调用 `ResourcePlane.observe_execution()`：

```text
输入：
  runtime_id
  success
  latency_ms
  observed_at
```

它会产生两类状态变化。

健康投影变化：

```text
ResourceHealthState:
  reliability = EMA(previous_reliability, success ? 1.0 : 0.0)
  latency_ms = EMA(previous_latency, observed_latency)
  last_heartbeat / updated_at = 当前时间
```

Runtime 快照变化：

```text
RuntimeSnapshot:
  observationSequence += 1
  observedAt = 当前时间
  latencyMs = 本次延迟
  reliability = 健康监控计算结果
  healthStatus = ONLINE（成功时）
```

存储写入采用乐观并发控制：

```text
读取 snapshot(version = N)
  -> 基于它生成 observationSequence + 1 的新快照
  -> update_snapshot(... expected_version=N)
  -> 成功：version = N + 1
  -> 冲突：转为 ResourceVersionConflictError
```

SQLite 被锁时会做有限次退避重试；最终失败时会把 Runtime 标记为不健康，并抛出显式的持久化错误。

## 整体数据状态机

```text
BindingManifest
  -> ExecutionRequirement
  -> CandidateDecision[]
  -> Lease
  -> ExecutionBinding
  -> Remote HTTP payload + HMAC headers
  -> AgentOutput / ResourceExecutionError
  -> RuntimeHealth + RuntimeSnapshot(version + 1)
  -> Lease release / expiry
```

## 关键结论

1. `ResourcePlane` 是资源事实和业务不变量的中心，但不负责实际执行。
2. `ResourceBinder` 是调度入口，负责从“需求”到“绑定 + 租约”。
3. `RuntimeProfile` 是静态能力声明，`RuntimeSnapshot` 是动态运行状态，两者分离且快照带版本。
4. 远程执行通过凭据、时间戳、请求体摘要和 nonce 完成 HMAC 防篡改与防重放。
5. 任务执行结果不会只返回给工作流，还会回写资源健康度，影响后续步骤的候选排序与可用性。
6. 当前资源组件实现了鉴权类和签名协议；实际远程 HTTP 服务端的路由接入点不在 `components/resource` 目录内，需在具体 Local Runtime / Edge Runtime 服务中确认其如何调用 `ResourceRequestAuthenticator`。
