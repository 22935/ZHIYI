## 实际依赖与实现

1. PostgreSQL、Redis 先同时拉起，再分别通过原有就绪检查。
2. 数据库就绪后拉起 Java、Vite 和受门禁约束的 AI 进程。
3. AI 进程提前导入固定模块白名单；不导入会立即装配 Runtime 的 `app.main`。
4. SQLite Schema 检查与工作区授权准备在两个临时线程中并行。授权准备等待 PostgreSQL 的实际权威表可见，
   并继续从 PostgreSQL 投影动态授权；表不可用、投影失败或 Schema 检查失败，均不放行 AI。
5. 两个准备任务完成并回收线程后，再启动 Host/Terminal 并原子写入本次启动专属的 release 文件。
6. AI 在同一进程中复用已加载模块，进入原有 `uvicorn.run('app.main:app', workers=1)`，执行原有装配、恢复和 readiness。
7. Java 整体 readiness、前端代理 readiness 仍须通过，之后打开 Electron。

release 文件只控制启动顺序，不替代 Run 执行许可。文件名按 session 隔离，内容为当前启动 nonce，
AI 同时核对启动器 PID 与创建时间。启动器消失、PID 复用、nonce 不符或超时均失败；最终清理本次 release/next 文件。

`app.execution.__init__` 改为按需解析原有公开导出。这样导入 `WorkspaceAuthority` 不再附带加载 Runtime/Coordinator，
公开函数和类的对象身份由回归测试验证。

并行准备共用的阶段计时器增加锁，保证诊断 JSON 写入串行。
服务停止改为明确依赖顺序：Desktop → Frontend → AI → Host → Terminal → Java → Redis → PostgreSQL，
避免把新的并行启动记录逆序误当成停止依赖。每个停止步骤也输出实际耗时。

## 预加载副作用审计

当前白名单为 uvicorn、FastAPI、执行装配定义、Coordinator 定义、AgentOS API 定义及 SDK 客户端定义。
真实独立 Python 子进程测试使用审计钩子和调用探针拒绝：

- SQLite 连接、网络连接、文件写入、目录创建和子进程启动。
- Python 后台线程启动、Runtime 装配和工作流实例锁取得。
- 在投影完成前读取并缓存工作区授权文件。

已有数据目录和首次无数据目录两种情况均通过；同时配置测试模型 Key，避免只验证缺少配置时的分支。
测试还确认不导入 `app.main`。

审计曾尝试提前加载 Chat/TTS，但 Chat 的数字人依赖会在导入时创建头像目录，真实探针明确拒绝。
因此这些模块仍留在门禁后的原启动流程中，没有放宽探针来容纳副作用。
这些检查属于白名单回归验证，不能把它们描述为生产进程中的通用沙箱。

## 实测及修正

首次并行试验额外等待了 Java 整体启动，再准备授权。Java 本次启动约 44 秒，
导致准备阶段等待约 47 秒，AI 放行反而变晚。保留该失败性能证据，随后将依赖修正为实际 PostgreSQL 权威表可用；
Java 全服务 readiness 继续作为最终门禁。

| 测量 | session | PostgreSQL 进程创建至最终 UP |
| --- | --- | ---: |
| 前一阶段 | `20261105T070555-b61e` | 76.21 秒 |
| 首次并行试验（等待整个 Java） | `20261105T111451-3a7e` | 106.22 秒 |
| 最终方案 | `20261105T112132-af82` | 68.45 秒 |

最终方案按相同起止定义观测减少约 7.76 秒（约 10.2%）。这些是单次历史测量，
期间机器负载、缓存、数据及其他工作区修改存在差异，不是严格同条件重复 A/B，不承诺固定收益。

AI 日志确认预加载用时 12.2 秒，在准备阶段内完成，之后等待 release，再进入 `app.main`。
首次通过完整 Java 检查的串行等待已消除；剩余主要耗时仍是门禁后的 AI 初始化和恢复。

最终启动器显示完整恢复 102.8 秒，其中停止旧服务约 33.6 秒，新启动段约 69.2 秒。
外层含 PowerShell 启动共 103.312 秒，退出 0。停止阶段中 Redis 耗时约 25.8 秒，保留原持久化退出策略。
首次试验的旧服务停止耗时 258.3 秒，多项旧服务超时后按既有身份校验规则终止；
最终试验各服务正常退出，没有通过缩短退出期限获得速度。
