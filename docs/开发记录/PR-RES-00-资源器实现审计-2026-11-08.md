## 3 结构性差异（需决策，不建议直接改代码）

### R1 · Agent×Node 多对多未实现，调度退化为「Runtime 单节点钉住」

设计 §3.3 明确"Node 与 Agent 之间不建立静态一对一关系"，§4.3 给 Agent 定义 `allowedNodeIds`
白名单，§7.2 要求**枚举合法 `(Agent, Node)` 配对**后再评分。

实现中 `RuntimeProfile` 只有单个 `node_id` 字段（`contracts/resource.py`），没有 `allowedNodeIds`；
`binder.evaluate:283` 直接 `self.plane.node(profile.node_id)` 取那一个节点做约束校验。

后果：
- 无法表达"同一个 Agent 部署到多个节点"，多节点只能靠登记多个 Runtime 变通；
- §7.2 第 5 步"只保留满足 Agent 节点白名单的节点"在语义上不存在（白名单退化为单点）；
- 配对枚举的成本优势（按节点容量分散）无从体现，调度实际是"按 Runtime 过滤 + 顺带校验其钉住的 Node"。

倾向：**改文档**。当前 Runtime 模型在端边云场景下可接受（Runtime ≈ 一次部署实例），把它写成
"Agent 部署实例"比硬改多对多更省钱；若要保多对多，需同时改合同、Store、租约槽位键（牵连 R3）。

### R2 · Node 账本缺「模型承载」与「节点类型、隐私等级、执行端点」

设计 §4.1 的 NodeProfile 含 `nodeType`、`privacyLevel`、`executionEndpoint`、`modelIds`，并特别
注明"`modelIds` 必须作为显式字段存在，不能仅存放在 metadata，否则调度器无法对模型约束做稳定校验"。

实现 `NodeProfile` 字段为：`node_id, display_name, placement, trust, compute(cpu/mem/gpu), location,
data_zone, data_region, owner_scope, labels, remote_execution_policy, enabled, metadata, version`。
`model_ids` 只在 `RuntimeProfile` 上；`hard_constraint_reasons` 没有任何节点侧模型判断。

后果：模型约束只在"模型端点候选"这条独立路径上校验（`assess` 里查 `model_candidates`），
**节点是否真能承载该模型不进硬约束**——同一节点的 Runtime 声明了模型，但节点本身可能在别处被
登记为不具备该模型，调度仍会通过。

倾向：**改代码**（补 `model_ids` 到 NodeProfile + 一条硬约束），风险中等，需迁移既有 `nodes` 表
（`node_store.py:245-250` 已有"无法按当前合同解析则重新登记"的处理，迁移成本可控）。

### R3 · 租约槽位按 Runtime 计，不按 `(agentId, nodeId)` 配对计

设计 §8.2「按 `(agentId, nodeId)` 计算活动槽位」，§4.6 要求租约携带 `agentId` 与 `nodeId`。

实现 `InMemoryLeaseCoordinator._slot_key` 返回 `f"resource:{resource_id}"`，容量取自
`profile.capacity`（Runtime 容量）；`ResourceLease` 无 `agentId`/`nodeId` 字段。

后果：多个 Runtime 共享同一物理节点时，**节点容量不设防**——每个 Runtime 各自看自己的容量，
节点总槽位可被超卖。这是 R1 的连带结果，不修 R1 而单修 R3 会引入两套容量语义。

倾向：**写进局限**，在文档把"租约作用域=Runtime"写成明确边界；真要多对多再一起改。

## 4 已确认缺陷与处置

### 4.1 已修复：存储层序号检查放行「等序覆盖」

- 现象：`node_store.update_snapshot` 原判断 `snapshot.observation_sequence < current`，等序观察可
  直接覆盖快照并 +1 版本；服务层 `observe_node` 虽拒绝 `<=`，但存储层是唯一写入边界，任何绕过
  Service 的调用（测试、运维脚本、后续新入口）都能写脏。
- 依据：设计 §4.2「服务端拒绝小于或等于当前值的观察」。
- 处置：改为 `<=` 抛 `StaleResourceObservation`，补回归用例
  `test_store_rejects_non_increasing_observation_sequence`（等序 3、退序 2 均拒绝，随后 4 正常 +1 版本）。
- 影响面：`tests/components/resource` + `tests/components/scheduler` 109 项通过；`tests/runtime`
  资源/绑定/租约相关 66 项通过。无行为回退。

### 4.2 未修复：`heartbeat_node` 不校验时间戳

`service.observe_node:356-368` 有完整校验（时区感知、未来偏差、回退告警），但同类的
`heartbeat_node:398-427` 直接使用 `observed_at`：既不做时区检查，也不拒绝未来时间。

后果：进程内路径传入未来时间会把 `observed_at` 写成未来值，`ResourceBinder.capacity_view:356`
用 `now - snapshot.observed_at` 判 `STALE`，结果恒为负 → 节点被永久视为新鲜，健康判定失效。

建议：把 `observe_node` 的时间校验抽成私有方法，两条路径共用。属低风险改动，但本轮未动
（进程内路径目前只用 `datetime.now`，无真实触发点，先记录）。

### 4.3 未修复：远程执行失败不回写 Node 失败计数

设计 §9.3「远程执行产生 `ResourceExecutionError` 时，Runtime 更新 **Node** 失败计数和健康状态」。
实现 `acg_execution.py:888-899` 只调 `set_runtime_health(..., healthy=False)`（必要时
`set_runtime_enabled(False)`）；`NodeSnapshot.consecutive_failures` 只由 `observe_node(success=False)`
更新，即由节点自报。

后果：反复执行失败的远程节点，只要自己的心跳仍报 success，节点账本始终健康，调度器会持续选中它。

建议：在失败分支追加 `plane.report_node_failure(node_id)`（写入 `consecutive_failures` + 触发
`NodeHealthMonitor` 降级），并在 `finally` 释放租约处保持现有 `retained_unknown` 语义。

## 5 文档漂移（不影响运行，但会让验收口径失真）

### R7 · §12.2 的实现状态段落已过期

文档称"部署层、数据区、owner、标签、成本、延迟及远程执行开关等步骤约束**尚未全部纳入**新调度器"。
实际 `binder.hard_constraint_reasons` 已覆盖：`NODE_DATA_REGION_MISMATCH`、`NODE_OWNER_SCOPE_MISMATCH`、
`NODE_LABEL_MISMATCH`、`COST_EXCEEDED`、`LATENCY_EXCEEDED`、`NODE_REMOTE_EXECUTION_DENIED`（含
`ALLOWLIST_ONLY` 白名单），以及 CPU/内存/GPU 类型/显存/信任等级/运行时种类/placement/data_zone/
owner_scope/labels/excluded_runtime_ids。

**唯一仍未接入的是 Node 侧 `modelIds`（R2）与 Node `placement` 的独立比较**。应按此改写 §12.2，
否则读者会按"未接入"去重复实现。

### R8 · 环境变量名与实现不一致

| 文档 §5.1/§10.2 | 实现（`apps/agent/app/execution/wiring.py:398-403`） |
|---|---|

| `AGENTOS_AGENT_DB` | `AGENTOS_RESOURCE_DB`（Runtime 账本沿用旧名） |
| 未提及 | `AGENTOS_RESOURCE_HEALTH_DB`、`AGENTOS_RESOURCE_HEARTBEAT_TIMEOUT_SECONDS` |

### R9 · 术语漂移：文档里的类名在代码中不存在

`AgentStore`、`AgentService`、`AgentDirectory`、`NodeService`、`TwoLayerSchedulerService`、
`NodeExecutionAdapter` 在代码中**全部不存在**。实际对应关系：

| 文档 | 代码 |
|---|---|
| `AgentStore` | `components/resource/store.py::ResourceStore`（`SQLiteResourceStore`） |
| `NodeService` + `AgentService` | `components/resource/service.py::ResourcePlane`（单一门面） |
| `TwoLayerSchedulerService` | `components/scheduler/binder.py::ResourceBinder` |
| `LeaseCoordinator` | `components/scheduler/leases.py` ✅（名称一致） |
| `NodeExecutionAdapter` | `adapters/resource_execution.py`（模块级，无同名类） |

维护者按文档 grep 会一无所获，这比"实现缺一块"更伤维护成本。建议文档加一张"术语对照"表。
