## 0 一句话定位

资源器是 AgentOS 执行内核中**资源事实的唯一权威入口**：登记资源、接收观测、判断可用性、做候选过滤与租约分配。它**不做工作流语义、不解释任务意图**——工作流、图结构、条件分支由 Planner / Executor / ExecutionRuntime 负责。

> ⚠️ 模型演进提示：合同 `contracts/resource.py` 开头明确写明——**"逻辑 Agent Role / Mission Planner / Coordinator 等逻辑角色不是资源，不出现在本合同"**。因此当前已是 **Node / Runtime / ModelEndpoint 三层分层模型**，与审计文档（2026-11-08）里"A g e n t / Node 两账本"的命名不同，这是阅读旧文档时必须先对齐的认知。

## 1 分层数据模型

| 层 | 概念 | 关键字段（见 `contracts/resource.py`） |
|---|---|---|
| Node | 部署实体：设备 / 边缘节点 / 云提供方 | `node_id`、`placement`(device/edge/cloud)、`trust`、`compute`(cpu/mem/gpu)、`labels`、`owner_scope`、`data_zone`/`data_region`、`remote_execution_policy`(allow/deny/allowlist_only)、`enabled`、`version` |
| Runtime | 承载实体：执行后端 / 模型服务 / 工具服务 | `runtime_id`、`node_id`(单点钉死)、`kind`(execution_backend/model_server/tool_service)、`capabilities`、`capacity`、`trust`、`placement`、`endpoint`、`owner_scope`、`domains`、`labels`、`cost_metadata`、`enabled`、`version` |
| ModelEndpoint | 可绑定模型路由目录 | `endpoint_id`、`provider`、`model`、`model_version`、`features`、`context_window`、`auth_reference` |
| 需求/绑定 | 任务要什么 / 拿到了什么 | `ExecutionRequirement`、`ExecutionBinding`、`RuntimeSnapshot`、`NodeSnapshot` |

关键关系：
- **Node 承载 Runtime**：一个 Runtime 只钉在一个 `node_id`（见 §5 R1）。
- **Placement（部署位置）与 RuntimeKind（逻辑类型）正交**：同是 `EXECUTION_BACKEND` 可部署在 device/edge/cloud，Placement 只是调度维度之一。
- 逻辑类型（`RuntimeKind`）与部署位置（`Placement`）**不是一对多关系**，而是两个独立调度维度。

## 3 核心逻辑流程

### 3.1 登记与严格所有权

- **本机引导路径**：`ensure_node` / `register_runtime` 幂等登记，打 `metadata.managedBy=bootstrap` 标记，可与快照槽位一起弹性扩缩容（capacity 变更带 `expected_capacity` 走 CAS）。
- **远程路径**：`register_remote_node` / `register_remote_runtime` 强制校验
  - placement 非 `device`（远程不能是本机类型）；
  - 必须声明 `owner_scope`；
  - 必须提供非 local 的可调用 endpoint。
  校验通过后签发**一次性凭据**：明文仅注册响应返回一次，存储 `secret_digest` + `encrypted_secret`（不存可直读明文）。
- **幂等与所有权**：`compute_registration_id` 提供幂等键，完全一致重复登记直接复用凭据；bootstrap 拥有的（进程内）与凭据保护的（远程）**互不静默覆盖**——冲突直接抛错，防进程内代码改写外部身份。

### 3.2 观测 / 心跳 / 健康

- **`observe_node`（远程签名观测）** 做完整校验：
  - 时区感知；未来时间拒绝并留 `time_anomaly_count` 计数；
  - 回退告警；严格递增 `observation_sequence`；
  - 存储层 `<=` 直接抛 `StaleResourceObservation`（审计修复项，仍有效）。
- **`heartbeat_node`（进程内）** 刷新快照，但**不做时间校验**——审计 4.2 已知遗留问题（当前进程内只用 `datetime.now`，无真实触发点，仅记录）。
- **健康判定规则**：**持久化快照是跨进程的权威源**，内存监视器仅当更新时才采用；按 `last_heartbeat` 距当前时间超过 stale/offline 阈值进行降级。
  - Runtime 健康状态：`UNKNOWN`（安全重启态）→ `ONLINE` / `DEGRADED` / `OFFLINE`。
  - Node 健康状态：`UNKNOWN` / `ONLINE` / `BUSY` / `OVERLOADED` / `STALE` / `OFFLINE` / `SUSPICIOUS`。

### 3.3 候选查询

- `runtime_candidates`：能力子集 + 健康 + 仍有槽位，按 `(-score, runtime_id)` 稳定排序。
- `model_candidates`：按 `ModelDemand` 过滤特性 / 上下文窗口 / 白名单 / 排除项，特征未声明按"不支持"处理。

### 3.4 调度（ResourceBinder）—— 单向职责链

```
ExecutionRequirement(任务要什么)
   → evaluate(只读：硬约束过滤 + 评分)
   → assess(就绪检查)
   → bind_ready(原子申请租约 + 版本复核 + 冻结 ExecutionBinding)
```

- **硬约束**（`hard_constraint_reasons`）覆盖两侧：
  - Node 侧：`enabled`、`NODE_UNHEALTHY`(UNKNOWN/STALE/OFFLINE/SUSPICIOUS)、`NODE_CPU/MEMORY/GPU_TYPE/GPU_MEMORY_INSUFFICIENT`、`NODE_LABEL/DATA_REGION/OWNER_SCOPE_MISMATCH`、`NODE_REMOTE_EXECUTION_DENIED`(含 `ALLOWLIST_ONLY`)。
  - Runtime 侧：`DISABLED`、`UNHEALTHY`、`CAPABILITY_MISMATCH`、`RUNTIME_KIND_MISMATCH`、`PLACEMENT_MISMATCH`、`TRUST_INSUFFICIENT`、`DOMAIN_MISMATCH`、`REMOTE_EXECUTION_DISABLED`、`NOT_ALLOWED`/`EXCLUDED`、`LABEL/DATA_ZONE/OWNER_SCOPE_MISMATCH`、`COST_EXCEEDED`、`LATENCY_EXCEEDED`。
- **`routing_hints` 只作有界先验**（权重固定 0.05），永远无法逆转硬约束排序——语义路由无裁决权。
- **评分权重**：可靠性 0.35、容量 0.20、空闲 0.15、延迟 0.10、成本 0.05、偏好 0.05、路由先验 0.05。
- **就绪结果**：`NO_ELIGIBLE_RESOURCE` / `NO_MODEL_ENDPOINT` / `NO_CAPACITY` / `COORDINATION_UNAVAILABLE`，不回退到未授权资源。

### 3.5 租约与并发控制

- **`InMemoryLeaseCoordinator`**：`RLock` 临界区，每次操作前 `_expire` 回收；同 `lease_id` 幂等返回既有租约；`active + slot_count > capacity` 返回 `None`；`_slot_key = "resource:{resource_id}"`——**按 Runtime 计容**。
- **`RedisLeaseCoordinator`**：每次分配一条 Lua 事务完成"清理过期 → 幂等判断 → 汇总活动槽位 → 容量校验 → `SET NX` + TTL → 写索引"。租约带 `owner_id`/`version`，支持 `LeaseKeepAlive` 异步续期（续期失败回调隔离）。
- **失败隔离**：租约状态单向（`active → released/expired`）；`finally` 中释放；未知结果走 `retained_unknown` 隔离，**绝不把"结果未知"当成功**。

## 4 与审计（2026-11-08）的对齐

审计结论"实现质量高于文档自述"的要点仍然成立，且已逐条核实：

| 设计条款 | 实现判定 |
|---|---|
| 认证顺序"凭据→ID→时间窗→HMAC→nonce→序号→CAS" | ✅ `auth.py` 严格按序，`hmac.compare_digest` |
| nonce 原子消费 | ✅ `BEGIN IMMEDIATE` + 主键冲突返回 `False` |
| 版本 CAS | ✅ `UPDATE ... WHERE id=? AND version=?`，`rowcount != 1` → `VersionConflict` |
| 观测序号防覆盖 | ✅ 持久化层 `<=` 抛 `StaleResourceObservation` |
| 租约幂等与容量 | ✅ 同 `leaseId` 直接返回；`active + slot > capacity` 返回 `None` |
| 失败隔离与租约释放 | ✅ `finally` 释放；`retained_unknown` 隔离 Runtime |

### 仍客观存在的结构性差异 / 遗留

| 编号 | 问题 | 现状 / 取向 |
|---|---|---|
| R1 | Agent×Node 多对多未实现 | 以 `Runtime.node_id` 单点钉住表达"一次部署实例"，多节点靠登记多个 Runtime 变通（端边云场景可接受） |
| R3 | 租约按 **Runtime** 计容，而非 `(agentId, nodeId)` 配对 | 多个 Runtime 共享物理节点时节点总槽位不设防（与 R1 同源） |
| 4.2 | `heartbeat_node` 不校验时间戳 | 已知，低风险，仅记录 |
| 4.3 | 远程执行失败回写 Node 失败计数 | 计划中（失败节点只要自己心跳报 success 仍会被选中） |
| R9 / 术语 | 审计文档类名（`AgentStore`/`AgentService`/`TwoLayerSchedulerService`）与代码不匹配 | 且模型本身已从 Agent/Node 演进为 Node/Runtime/ModelEndpoint——文档需补"术语对照 + 模型变更" |
